# Интеграции

Все интеграции подготовлены как интерфейсы с демо-реализацией. Реальные API внешних систем здесь **не выдуманы**:
для каждой указано, что нужно согласовать.

## E-Shanyraq

Действующий E-Shanyraq не изменялся. Репозиторий изучен только для согласования терминов:
иерархия «ЖК → корпус → подъезд → этаж → квартира → помещение», роли `resident / dispatcher / manager / developer / admin`,
таблица `passport_records` с категориями `equipment / hidden_work / document / service / plan`.

**Переход из личного кабинета** — ссылка:

```
https://academy.example.kz/?source=eshanyraq&apartment=72&ticket=<одноразовый билет>
```

* `apartment` — номер или идентификатор квартиры в академии (`data/complexes`).
* `ticket` — одноразовый билет единого входа. Браузер его не проверяет: следующий шаг — эндпоинт сервера академии,
  который обменивает билет на сессию через E-Shanyraq (`EShanyraqClient.exchangeTicket`). Формат билета нужно согласовать.
* `role` в ссылке используется только в демо; в рабочем режиме роль приходит из E-Shanyraq (`mapEShanyraqRole`).

**Синхронизация паспорта** — `toEShanyraqPassportRecord()` формирует запись, совместимую с `passport_records`
(`category`, `title`, `details jsonb`). Файлы передаются отдельно — по аналогии с `passport_files`.

**Заявки и оборудование** — оформленный заказ содержит помещение, позиции, гарантию; при подключении он может
создавать заявку в E-Shanyraq, а установленное оборудование — запись категории `equipment`.

Что нужно от команды E-Shanyraq: эндпоинт обмена билета, эндпоинт записи в паспорт (или доступ к существующему API),
соответствие идентификаторов квартир (uuid ↔ номер в академии).

## Naidu.kz — «Найти дешевле»

`src/integrations/naidu/PriceComparisonAdapter.ts`

* Запрос (`PriceQuery`): `productId, sku, name, unit, packSize, qty, specs, city`.
* Ответ (`Offer[]`): `offerId, sku, name, seller, unit, packSize, price, inStock, deliveryPrice, deliveryDays, specs, updatedAt`.
* Сравнение в академии: артикул, ключевые характеристики, единицы (пересчёт цены упаковки в цену за м² и т. п.),
  количество с кратностью, наличие, доставка, итоговая стоимость, дата обновления.
* Несовместимый аналог показывается с причинами, но **не подставляется** в смету.

Сейчас работает `DemoNaiduAdapter` (тестовые предложения из `data/naidu/offers.csv`).
`NaiduHttpAdapter` включается переменной `VITE_NAIDU_ENDPOINT`, когда будет согласован формат.
Если ответ Naidu.kz отличается от `Offer`, пишется маленький преобразователь внутри адаптера — остальной код не меняется.

Совместные закупки жильцов одного ЖК не реализованы; заготовка — группировка одинаковых `productId` по `complex.id`.

## «Город мастеров» — заказ

`src/integrations/gorodmasterov/orders.ts`

* `freezeOrder()` фиксирует строки сметы, итоги, источник и время цен.
* Статусы: отправлен → принят мастером → выполнен (или отменён жильцом). Переходы проверяются по роли.
* Выполненный заказ добавляет в цифровой паспорт оборудование и материалы с датой окончания гарантии;
  мастер добавляет фото скрытых работ и акт.
* `demoGateway` ничего не отправляет и не принимает оплату. Реальный шлюз реализует `OrderGateway.submit()`
  после согласования API «Города мастеров».

## Хранение файлов

В прототипе фото и документы паспорта хранятся в IndexedDB браузера (сжатие фото до 1920 px, проверка типа и размера).
Для рабочего режима — `PassportRepository` с серверной реализацией: файлы вне публичной папки, случайные имена,
проверка MIME, ограничение размера, выдача по подписанным ссылкам после проверки прав.
